# TickDeck PRD 安全与数据治理专项评审

## 评审结论

**Verdict：BLOCK — 当前 PRD 不应直接通过 v1.0 公开发布安全门禁。**

文档已经建立了正确的方向性边界：数据能力随源而定、商用数据不随项目分发、Agent 有 R0–R3 风险模型、脚本按不可信代码处理、秘密不进入浏览器或 Agent、单工作区不冒充多租户。这些不是空白，也明显优于只写“注意安全”的一般 PRD。

但 launch 级要求仍缺少两类不可后移的产品契约：

1. 商用数据的许可用途尚未成为贯穿查询、缓存、派生、模型发送、导出和删除的可执行策略；现在的“能力矩阵 + 合同核验”不足以防止系统合法取数后非法外发或长期留存。
2. “反向代理认证 + 本地回环监听”没有形成应用层请求安全边界；本地浏览器攻击、代理绕过、CSRF、WebSocket/SSE、错误信任转发头等场景没有门禁。

在修复 2 个 Critical 和 8 个 High 项、并把相关测试加入 v1.0 发布门槛前，不建议将此 PRD 交给架构阶段作为已经闭合的安全合同。本文为产品与安全评审，不代替具体供应商合同或法律意见。

## 分级统计

| 严重度 | 数量 | 发布含义 |
|---|---:|---|
| Critical | 2 | 未修复不得公开发布，也不得把真实商用连接器标为可用 |
| High | 8 | v1.0 RC 前必须形成明确产品契约和可重复验收 |
| Medium | 4 | 应进入架构与 Epic，最晚在公开 beta/RC 的相应门槛前关闭 |
| Low | 1 | 文档澄清项，可随本轮修订完成 |

## Critical findings

### SEC-DATA-001：许可用途没有成为可组合、可继承、默认拒绝的执行策略

- **位置：** PRD FR-002、FR-004、FR-019、FR-024（第 130、132、157、167 行）；数据治理 8.1（第 270–275 行）；风险表（第 374–375 行）；addendum 数据授权边界（第 40–79 行）。
- **问题：** “许可用途”目前只是能力矩阵中的一个声明字段，正文没有定义许可维度、策略优先级、默认值、到期条件和执法点。系统可能在连接器允许“本地显示”时，仍把原始行情、全文资讯或派生结果送入外部模型、写入长期缓存、嵌入回测产物、通过 Webhook 或 CSV 再输出。多连接器混合结果、派生指标和 Agent 总结也没有继承最严格限制的规则。成熟度“正式授权验证”也容易被错误理解为持续有效的运行时授权。
- **影响：** 可以在没有绕过账号或配额的情况下，依然违反缓存、派生、外发、多人共享、订阅终止或再分发条款；这正是 PRD 声称要阻止的核心风险。由于 v1.0 面向真实外部用户且允许自带商业数据，这是 release blocker。
- **修复：** 新增稳定的 `DataUsePolicy` 产品契约，至少逐数据集/字段声明 `display`、`local_compute`、`cache_ttl`、`persist_raw`、`persist_derived`、`export`、`webhook`、`external_model`、`trusted_workspace_share`、`public_display`、`retention_after_expiry`，附授权依据、授权主体、合同/策略版本、生效期与复核时间。未声明一律拒绝；合并与派生结果继承最严格策略。查询、缓存、产物保存、Agent 上下文组装、导出、通知和备份必须调用同一服务端策略判定，并将“允许/拒绝 + policy version”写入审计。
- **验收：** 建立许可策略矩阵的自动化测试：对每种数据用途、混合来源、过期/撤销授权、订阅终止和派生产物验证默认拒绝、限制继承和清理；任何绕过统一策略层的代码路径阻止发布。真实连接器只有合同映射完成且这些测试通过，才能从“试用验证”提升为“可用于对应场景”。

### SEC-AUTH-002：反向代理说明不是应用层访问控制，本地与远端都缺少请求来源防护

- **位置：** UJ-3（第 72–74 行）；FR-071、FR-072（第 249–250 行）；addendum 交付边界（第 18–25 行）；风险表“单工作区”（第 379 行）。
- **问题：** PRD 将远端认证完全交给代理，却没有要求 TickDeck 验证请求确实来自受信代理，也没有规定 Origin/Host 校验、CSRF 防护、WebSocket/SSE 鉴权、转发头信任范围或直连端口拒绝。即便只监听回环，恶意网页仍可能通过浏览器访问本地服务、利用宽松 CORS、DNS rebinding 或无 CSRF 的状态修改接口。远端部署若错误暴露上游端口，全部持久化与模拟订单能力会在无应用层门禁下暴露。
- **影响：** 攻击者可能无需知道数据或模型密钥，就能让已登录浏览器保存/删除产物、触发费用、发送通知或提交模拟订单。仅靠文档提醒无法满足 launch 级默认安全。
- **修复：** 在“不建设用户体系”前提下仍需定义最小实例访问边界：首次启动生成或由部署者设置的实例级访问密钥/受保护会话；远端模式只信任显式配置的代理来源与身份头；默认拒绝未授权直连；严格 Origin/Host allowlist、CSRF token、SameSite/HttpOnly/Secure cookie、WebSocket/SSE 同等校验；默认关闭跨域；只信任列出的 `Forwarded`/`X-Forwarded-*` 跳数。若选择纯代理鉴权，则进程必须支持 Unix socket/私网绑定并在远端模式缺失代理断言时拒绝启动或持续显示阻断性告警。
- **验收：** 在本地与参考远端部署上自动测试跨站 POST、WebSocket、DNS rebinding、伪造转发头、直接访问上游端口、代理会话过期和错误 Origin；任何状态修改或 Agent 执行成功都判定失败。把此套件加入 v1.0 安全门槛，而不只放入部署文档。

## High findings

### SEC-EGRESS-003：外部模型、Webhook 与自定义端点缺少统一出站和数据最小化控制

- **位置：** FR-027（第 175 行）、FR-059（第 227 行）、FR-065（第 238 行）、FR-068–069（第 241–242 行）、数据治理 8.1（第 273 行）。
- **问题：** R2 只覆盖“向新外部服务发送数据”，意味着服务一旦配置，后续任务可在 R0 中持续发送未知范围的数据。PRD 没有要求模型或 Webhook 调用前显示/记录实际数据类别、最小化载荷、脱敏字段、提供商留存/训练策略和数据驻留；也未限定自定义 Base URL、重定向、DNS 解析、云元数据地址、回环/内网地址以及跨主机携带认证头。Webhook 同样可能成为 SSRF 或许可数据外泄通道。
- **影响：** 数据可能在用户未理解的情况下进入第三方留存/训练系统，或被发送到内网管理接口和云元数据服务；授权数据、研究偏好和服务凭据都可能泄露。
- **修复：** 定义统一的 `EgressPolicy`：服务端按目的端、数据分类、字段、数量、授权策略和会话范围判定；新目的端首次 R2，后续授权必须有明确范围/有效期且可撤销；默认仅发送完成任务所需的聚合或引用，不发送原文/全量时序。连接配置测试显示提供商、主机、数据类型、预计留存和费用。URL 解析后阻止非预期协议、回环、链路本地、云元数据和私网目的地（部署者可显式收紧范围内放行）；限制重定向且不得跨主机转发秘密头。Webhook 需签名、幂等、载荷预览和最小化。
- **验收：** 覆盖 DNS rebinding、重定向偷取头、IPv4/IPv6 内网编码、模型上下文误带全文/密钥、已撤销授权、Webhooks 重放和混合许可数据的自动化测试。

### SEC-AGENT-004：风险级别的权威判定与 R1/R2 授权主体仍不明确

- **位置：** FR-057–063（第 225–231 行）；FR-078（第 261 行）；8.2（第 277–281 行）；NFR-017（第 323 行）。
- **问题：** 工具/扩展自行声明风险与权限，但 PRD 没有说明由哪个受信、不可被模型或扩展降低的服务端策略计算“有效风险”。参数变化可能把同一工具从只读变成高成本或外发；受信扩展若错误标成 R0，当前合同没有强制上调机制。与此同时，一实例无用户身份，R1 的“用户授权”无法自然绑定到批准者；浏览器标签页、代理主体、Agent run 和重启后的授权是否共享不清楚。
- **影响：** 会产生错误降级、授权跨会话复用、他人撤销/使用授权，或在参数被工具执行前重写后继续使用旧批准。
- **修复：** 要求服务端策略引擎根据工具 ID/版本、参数、成本上界、数据用途、目标对象和外部目的端计算最终风险，扩展只可建议、不可降低平台最低级别；R3 平台规则不可覆盖。R1 必须明确是实例级、代理主体级还是短期浏览器会话级；若无稳定主体，默认只能是当前 Agent run/当前受保护会话，且重启失效。审批对象使用规范化参数哈希、状态版本、单次 nonce、到期时间和 compare-and-swap，执行前再次判定风险与状态。
- **验收：** 测试参数篡改、工具升级、费用估算变化、组合状态变化、两个浏览器会话并发审批、审批重放、断线恢复和恶意扩展低报风险。

### SEC-SANDBOX-005：沙箱原则扎实，但发布验收可被“已知用例”轻易弱化

- **位置：** FR-031–035（第 184–188 行）；8.3（第 283–287 行）；NFR-016（第 322 行）；SM-07（第 354 行）；addendum 沙箱边界（第 136–152 行）。
- **问题：** 文档已明确不能仅依赖 `node:vm`、Node Permission Model 或某个库，这是优点；但“已知逃逸用例为 0”没有定义测试语料、支持平台、攻击面、资源阈值和失败隔离观察窗口。若测试集为空或只跑语法用例也能形式上通过。TypeScript 编译链、允许依赖、动态代码生成、WASM、原生模块、宿主对象注入、IPC 和运行产物回传没有纳入验收合同。
- **影响：** 架构可以选择弱隔离实现并声称符合 PRD，直到真实恶意脚本读取宿主数据、横向访问服务或拖垮进程。
- **修复：** 在 PRD 加入沙箱安全验收规范：正式支持的 OS/发行形态；独立故障域；只读最小镜像/临时目录；默认无网络、无宿主挂载、无环境继承、非特权身份；允许 API 的 capability 清单；固定编译器与依赖；禁止 native addon/未批准 WASM/动态模块；CPU、内存、进程、文件、输出与墙钟硬限制；超限后强制终止和清理。维护公开与私有对抗语料并规定类别，而不是只写“已知”。
- **验收：** CI 中对每个支持部署模式执行逃逸、原型链/宿主对象、动态导入、依赖投毒、fork/线程、文件/网络、IPC、内存/CPU/输出炸弹和并发耗尽测试；同时发起正常 API/Agent/存储请求验证主服务和其他运行的延迟/完整性未越界。

### SEC-SECRETS-006：秘密生命周期、备份与恢复要求存在未解决的冲突

- **位置：** FR-065（第 238 行）、FR-074–076（第 252–254 行）；NFR-014–015（第 320–321 行）；addendum 部署问题（第 36 行）。
- **问题：** “服务端秘密存储”没有定义静态加密、文件权限、主密钥来源、轮换/撤销、引用方式和错误路径脱敏。FR-074 要求完整工作区备份恢复，而 FR-075 又禁止秘密进入导出，未说明备份是否包含凭据：包含则可能明文泄漏，不包含则恢复后不能称完整。自定义请求头也可能携带秘密，但当前只点名 API Key。
- **影响：** 备份、诊断、迁移、崩溃栈、连接测试或扩展配置最容易成为凭据泄漏路径；缺少轮换会放大事故窗口。
- **修复：** 把所有 API Key、Token、Cookie、证书私钥和敏感自定义头统一为 secret reference；定义本地文件/容器 secret 后端的最小权限与静态保护，支持添加、测试、轮换、吊销而不回显。明确两种备份模式：默认排除秘密并生成“需重新配置”清单；可选包含秘密时必须用独立用户口令/密钥加密、禁止与包同存并测试恢复。日志/诊断/错误对象只保留密钥指纹和 secret ID。
- **验收：** 自动扫描浏览器响应、Agent 上下文、日志、审计、诊断包、普通备份、错误栈和模拟记录；注入已知 canary secret 后任何明文命中即失败。测试轮换后旧凭据失效、恢复后秘密引用状态明确。

### SEC-SUPPLY-007：“受信扩展”把供应链风险转嫁给部署者，但没有形成可验证安装边界

- **位置：** UJ-4（第 76–78 行）；FR-077–083（第 260–266 行）；NFR-018、NFR-027–029（第 324、339–341 行）；addendum 扩展取舍（第 162–171 行）。
- **问题：** 扩展有权限清单和契约测试，但“受信代码”似乎可在 Fastify 服务权限内运行，权限清单可能只是说明而非强制隔离。没有要求来源、版本锁、完整性校验、SBOM、依赖审查、安装/升级前后权限 diff、禁用/回滚、凭据按扩展最小授权和发布撤回机制。NFR-018 只看“已知严重漏洞”，却没有漏洞源、严重度口径、例外到期或传递依赖范围。
- **影响：** 一个被接管或 typo-squatted 的扩展/依赖可以读取全部数据和模型秘密、绕过 Agent 风险策略或修改审计记录；提醒“这是受信代码”不足以降低后果。
- **修复：** v1.0 至少要求扩展从显式本地路径/锁定包安装，默认禁用；记录来源 URL/提交或包版本/内容哈希/签名状态/SBOM；安装和升级展示权限 diff并需部署者确认；扩展仅获得自己声明且批准的 secret references 与 API capabilities，不直接读取全局秘密存储。支持 kill switch、隔离启动失败、回滚和撤回列表。若 v1 架构确实允许任意进程内代码，则 PRD 必须醒目标明它拥有完整 TickDeck 服务权限，并禁止将权限清单描述为强制边界。
- **验收：** 篡改包、依赖替换、权限升级、撤回版本、扩展崩溃、扩展读取未授权秘密和扩展绕过策略引擎的测试必须失败关闭。

### SEC-AUDIT-008：审计“可查询”但不保证完整性、主体来源或与副作用的一致提交

- **位置：** FR-048（第 211 行）、FR-061–064（第 229–232 行）、FR-073（第 251 行）、NFR-009–010、NFR-017（第 312–314、323 行）。
- **问题：** 没有要求审计追加式/防篡改、单调序列、可信时间、关联 ID、actor/source、原始批准摘要、策略版本和副作用事务状态。无内部用户体系时至少要区分直接 UI、Agent run、后台提醒、扩展和代理传入主体；现在只有“手动或 Agent”的脚本作者来源。也未说明模拟订单、审计和组合账本是否原子提交，崩溃可能出现“执行但未记审计”或相反。
- **影响：** 安全事件无法重建，审批越权无法归因，模拟组合可能在重试/崩溃后与订单历史不一致，SM-06 也无法可信取证。
- **修复：** 定义最小审计 schema：事件 ID/序列、UTC 时间与时钟状态、实例/代理主体或匿名受保护会话、来源类型、Agent run、工具/版本、规范化参数摘要、数据策略版本、风险级别、批准 ID、幂等键、前后状态版本、结果/失败、费用和关联事件。采用追加式记录与受控保留；高风险副作用使用事务 outbox/等价机制，使状态、审计和通知可恢复地一致。审计删除/导出本身需记录且默认不能由 Agent 执行。
- **验收：** 断电点注入、并发订单、重复回调、数据库重试和时钟异常后，审计、订单与组合状态必须一一对账；篡改检测和敏感字段脱敏同时通过。

### SEC-RETENTION-009：留存、授权终止和可复现性之间没有确定的产品行为

- **位置：** FR-037、FR-042（第 195、200 行）；FR-073–075（第 251–253 行）；8.1 第 275 行；NFR-011–012（第 314–315 行）；OQ-04（第 388 行）。
- **问题：** PRD 一方面希望保存数据/运行清单以复现，另一方面要求按授权执行删除，但没有数据资产清单、TTL、删除范围和优先级。原始缓存、索引、衍生指标、Agent 引用、回测快照、审计、普通备份和已导出包是否同步清理未定义；订阅终止后是保留哈希、聚合结果、完全删除还是冻结访问也不明确。
- **影响：** 可能在订阅结束后继续持有或泄露受限数据，也可能为了清理而让历史报告无解释地变化，破坏研究可信度。
- **修复：** 定义数据生命周期状态机和资产 inventory：采集、缓存、派生、固化、导出、过期、撤销、待清理、已清理。许可策略决定每类资产 TTL 与可保留形式；删除作业覆盖数据库、对象、搜索索引、任务缓存和备份到期策略。运行清单只承诺保存可合法保留的哈希/版本/摘要；源数据不可得时报告变为“不可完全复现”且不偷偷换源。部署者能预览清理范围并取得不可逆确认和结果报告。
- **验收：** 用带短期授权的 canary 数据贯穿筛选、模型、回测、通知、导出和备份，授权到期后检查所有受管副本与派生限制，历史产物明确降级且审计完整。

### SEC-INJECT-010：提示注入只有结果陈述，没有覆盖数据到工具参数的测试合同

- **位置：** FR-053–054（第 221–222 行）、FR-059–061（第 227–229 行）、FR-064（第 232 行）、FR-079（第 262 行）、NFR-013、NFR-029（第 319、341 行）。
- **问题：** “资讯或工具结果中的指令性文本不得改变 Agent 权限或系统行为”方向正确，但没有说明原始新闻/公告/连接器错误/扩展描述均为不可信数据，也没有要求模型生成的每个工具参数在执行前再次经过 schema、权限、数据策略和风险判定。攻击文本未必直接“改变权限”，仍可诱使 Agent 批量导出、调用已授权 Webhook、消耗预算、选择错误标的或在报告中隐藏来源。
- **影响：** 即便 R3 永远禁止，攻击者仍可滥用现有 R0/R1 范围，造成数据泄露、费用消耗和研究结果操纵。
- **修复：** 给所有上下文片段标注来源与信任级别；第三方内容只进入 data channel/结构化字段，不能拼入系统或开发者指令；工具参数必须由服务端校验并在执行瞬间重新授权，模型文本绝不携带权限。对批量读取/外发/高成本设置速率与数据量阈值。报告必须保留来源引用，未验证的网页指令不进入策略代码或扩展安装流程。
- **验收：** 建立中英双语间接提示注入集，覆盖公告、新闻、股票名称、供应商错误、工具返回和文档附件；测试跨工具链、持久化记忆、已存在 R1 授权、编码/隐藏文本与多轮攻击，验证无未批准副作用或来源隐藏。

## Medium findings

### SEC-SIM-011：模拟交易账本缺少不可逆事件与更正语义

- **位置：** FR-046–051（第 209–214 行）；NFR-009–010（第 312–314 行）。
- **问题：** 幂等和历史记录已提出，但重置组合、回补行情、公司行动修订、撤单与部分成交重放的更正方式未定义。若直接重算/覆盖历史，用户无法区分当时可见信息和事后修订。
- **修复：** 要求订单、成交、现金、公司行动与人工更正采用稳定事件 ID 和追加式更正；重置创建新账本世代而不覆盖旧记录。组合估值明确 `as-of` 数据时间、接收时间和修订版本。
- **验收：** 对乱序行情、重复成交、部分成交后撤单、公司行动回补、回滚升级和组合重置做账本恒等式及历史可追溯测试。

### SEC-DATA-012：能力矩阵把技术成熟度与法律授权状态混在同一展示语义

- **位置：** FR-002–003（第 130–131 行）；词汇表能力矩阵（第 85 行）；风险表（第 374–375 行）。
- **问题：** “试用验证 / 正式授权验证 / 允许再分发”既包含集成成熟度又包含特定部署者的合同状态。项目维护者验证过某厂商并不代表每个部署实例、账号、用途和时间点都获授权。
- **修复：** 分成两条正交轴：`implementationMaturity`（stub/tested/supported）和部署实例的 `entitlementState`（unknown/active/restricted/expired/revoked），再由 DataUsePolicy 表达具体用途。UI 禁止以绿色“可用”合并三者。
- **验收：** 切换账号、合同过期、用途收紧或连接器升级后，功能立即重新判定且不沿用旧 entitlement。

### SEC-PRIV-013：没有数据清单、隐私说明和第三方处理者披露的最小要求

- **位置：** 产品原则第 29 行；FR-069、FR-075（第 242、253 行）；NFR-019（第 325 行）；OQ-04（第 388 行）。
- **问题：** 默认无遥测很好，但自选、策略、组合、提示、代理身份头和日志仍可能构成个人或高敏研究数据；外部模型、通知服务和数据厂商是不同处理者。把隐私文本推到 beta 前才核对，不足以指导数据模型和导出设计。
- **修复：** 在架构前定义数据清单和流向图要求：数据类别、目的、存储位置、默认留存、外部接收方、删除/导出方法。公开 alpha 至少提供自托管责任边界、外部模型会收到什么和默认关闭遥测的准确说明。
- **验收：** 每个外部请求和持久化表可映射到清单；新增字段/第三方集成在 CI 或发布清单中必须更新数据流说明。

### SEC-OPS-014：安全响应与版本支持直到 RC 才定义，晚于公开 alpha 的真实暴露

- **位置：** NFR-018（第 324 行）；OQ-06（第 390 行）；0.x 可公开渐进交付（第 111 行）。
- **问题：** 公开 alpha 已包含不可信脚本、扩展、数据和模型凭据，已经可能收到真实漏洞报告。到 RC 才定义报告渠道和修复规则会让早期用户无处安全披露，也无法判断受影响版本。
- **修复：** 将最小 `SECURITY.md`、私密报告渠道、支持版本、依赖严重度口径、紧急禁用方式和密钥泄漏处置提前到首个公开 alpha；RC 再完善 SLA 可以接受。
- **验收：** 发布清单验证渠道可用、维护者能收到私密报告、受影响功能可禁用、补丁与公告流程完成一次演练。

## Low finding

### SEC-NFR-015：安全 NFR 与反指标中的“严重”“已知”“已确认”缺少统一判定口径

- **位置：** NFR-018（第 324 行）；SM-07（第 354 行）；SM-C02（第 364 行）。
- **问题：** 不定义漏洞数据库、CVSS/供应商严重度、扫描时间、误报接受人、例外期限和“确认”责任人，会让门禁因团队不同而漂移。
- **修复：** 在发布测试计划中规定漏洞源和锁文件/SBOM扫描范围、严重度算法、扫描新鲜度、误报证据、例外审批与到期；沙箱逃逸和密钥泄露不得以普通风险接受豁免。
- **验收：** 用一项已知严重依赖、一个误报和一个过期例外跑通门禁，结果必须确定一致。

## 建议加入 v1.0 发布门槛的最小安全包

在不提前指定架构实现的前提下，PRD 至少应要求以下可重复证据：

1. **数据许可门禁：** 每个正式连接器具有合同用途映射、策略版本、到期/撤销行为和跨查询—缓存—模型—导出—备份的自动化用例。
2. **请求边界门禁：** 本地与远端参考部署通过 Origin/Host/CSRF/WebSocket/代理绕过和转发头测试。
3. **Agent 授权门禁：** R0–R3 全矩阵覆盖动态参数、并发、重放、状态变化、工具升级、扩展低报和预算变化，而不只测“R2 未确认 = 0”。
4. **沙箱门禁：** 明确攻击类别、支持平台、硬资源阈值和主服务无影响阈值；公开与私有用例均执行。
5. **秘密与出站门禁：** canary secret 扫描所有响应/日志/导出/备份；SSRF、重定向、DNS rebinding、跨主机凭据和许可数据外发测试通过。
6. **审计与账本门禁：** 故障注入后审批、工具执行、订单、成交、组合状态和审计可一一对账，且审计不泄漏敏感数据。
7. **供应链门禁：** 锁文件、SBOM、来源/完整性、权限 diff、撤回/禁用/回滚和严重漏洞政策有可复查证据。

## 可以保留的现有设计

- FR-003 对未联调连接器不显示为可用，以及 addendum 对 Wind、Choice、iFinD 仅能做中立契约和 mock 的表述，应保留。
- FR-061 将批准绑定到精确参数、运行、状态、工具版本和有效期，是正确基础；修复重点是主体、nonce、并发和服务端最终判定。
- FR-075 的“不进入浏览器、Agent、普通日志、导出或模拟记录”应保留，并用 secret lifecycle 与 canary 测试补全。
- 8.3 与 addendum 明确否定 `node:vm`/Permission Model 单独作为安全机制，应保留；修复重点是让 SM-07 不可被空测试集满足。
- 单工作区、不提供 RBAC 的范围是诚实的，可以保留；但不能据此省略实例访问、浏览器来源和代理旁路防护。
