# PRD Quality Review — TickDeck

## Overall verdict

这是一份内容扎实、边界诚实、对数据授权、Agent 风险与沙箱安全尤其清醒的能力型 PRD；它已经足够支持探索性架构和 UX 工作。它尚不适合直接为完整 v1.0 开发开绿灯：最大的风险不是漏功能，而是以 83 项功能要求投入一个仍未被用户证据验证的产品命题，同时缺少可在大规模建设前触发继续、收缩或停止的验证门。

## Decision-readiness — adequate

产品选择大多写成了明确承诺：A/港股一等支持、八组能力同时构成 v1.0、实盘与多租户排除、数据和模型由部署者自带、Agent 按 R0–R3 治理。`§6.3`、`§8`、`§11` 和 addendum 的“已排除或延期的替代方向”也确实说明了放弃什么以及为什么，决策者无需从模糊措辞中猜测边界。

不过，“所有八组能力缺一不可”把 83 个 FR 变成了一个单体发布承诺，而文档只说 0.x 可以渐进交付，没有定义先验证哪条风险链、何时砍掉或收缩一组能力。对正式外部发布项目而言，这使决策者知道终点，却还不能判断应批准哪一段投入。

### Findings

- **high** 缺少依赖有序的 0.x 决策门与可砍范围（§6.2、§11）— 文档把八组能力都设为 v1.0 必备，但没有定义哪一个最小闭环先证明 Agent 差异化、数据可行性与沙箱安全，也没有失败后的缩减规则；“每个预发布版本公开能力缺口”只是披露机制，不是投资决策机制。*Fix:* 增加 2–4 个按风险依赖排序的 alpha/beta 门，每个门写明所验证命题、进入条件、退出指标，以及未通过时继续、收缩或停止的规则。
- **medium** “开放项均不阻止下游”是过宽的统一判断（§12）— OQ-02 决定图表、指标和绘图 Epic 的实际边界，OQ-03 会反向约束连接器能力与部署形态；二者未解决时可以探索，但不足以冻结对应故事或发布承诺。*Fix:* 为每个 OQ 分别标注可继续的下游活动、受阻活动和最晚关闭门，而不是统一声明“不阻止 UX、架构与 Epic 拆分”。

## Substance over theater — strong

内容基本都由 TickDeck 的真实矛盾驱动，而非模板家具。四条旅程分别改变了研究、策略、部署和贡献要求；NFR 给出了环境与阈值；数据授权、模型能力分级、模拟交易、脚本隔离和受信扩展均有产品特有的行为后果。愿景中的“工具闭环 + 可审计 Agent”也贯穿到 FR、风险与成功指标，没有出现空泛的“安全、可靠、可扩展”陈列。

## Strategic coherence — thin

文档有清楚的产品 thesis：A/港股范围内的一体化研究闭环是基础门槛，全工具、可审计的 Agent 是差异化。功能优先级总体服务该 thesis，SM-04 至 SM-07 也避免用回测收益、Star 或功能数量代替质量。

但 addendum 已诚实承认这只是“当前差异化假设，不是市场需求已经被验证的证明”。PRD 仍把需求验证放到完整 v1.0 发布后的 SM-08；安装、任务完成率和生成成功率能证明产品可用，却不能证明目标用户愿意承担自托管、数据授权和模型配置成本，从现有工具迁移到 TickDeck。对于如此宽的正式发布范围，这个验证顺序是核心战略缺口。

### Findings

- **critical** 核心价值假设没有前置验证门（§1、§10；addendum“竞品与邻近方案证据”）— 当前证据只说明组合形态可能少见，没有证明进阶投资者或量化开发者在承担部署与数据成本后仍持续需要“一体化工具 + Agent”，而 SM-08 要到 v1.0 发布后才验证重复使用。*Fix:* 在完整能力建设前增加明确的需求验证里程碑：用可点击原型或薄闭环让目标用户完成选股和策略任务，测量相对现有工作流的时间/错误改善、配置后启用率、二次任务复用和迁移意愿，并预先写明未达阈值时缩小、转向或停止的规则。

## Done-ness clarity — adequate

多数 FR 至少包含一个可观察结果，R0–R3、运行清单、回测披露、审计和模拟撮合的要求尤其具体；NFR 也普遍使用了数值边界。这比一般能力清单更接近可验收合同。

不过，两个横跨产品的验收面仍未冻结：一是“连接器能力随源而定”没有对应 v1.0 的最低数据能力基线，二是图表/指标目录以及若干“检测或警示”类要求没有可枚举的覆盖标准。基准任务和性能指标也缺少可复跑的测试协议，因此表面上的数字还不能直接成为放行判据。

### Findings

- **high** v1.0 没有最低可用数据能力画像（§6.1、FR-002–FR-007、FR-009、FR-016、FR-020–FR-024）— “以能力矩阵为准”允许正确降级，但没有说明正式发布至少必须有哪种 A 股与港股数据、何种历史深度/时效/公司行动/基本面覆盖；理论上只有演示数据或极浅连接器也可能声称八组能力已完成。*Fix:* 定义一个供应商中立的 v1.0 reference capability profile，并分别标明演示验收与真实授权连接器验收的最低市场、字段、周期、历史、时效、完整性和许可要求。
- **high** 核心工具目录与偏差检查仍无法据此验收（FR-013、FR-029、FR-040、OQ-02）— “核心绘图工具”“常用指标”“检测或警示”没有列出 v1.0 覆盖集、检测结果等级或不可检测时的行为，而 OQ-02 又计划在 Epic 拆分前才冻结，当前无法可靠拆出完整故事或测试。*Fix:* 在 PRD 附上版本化的最小目录和偏差检查矩阵，逐项定义支持、警示、无法判定及验收样例；若目录单独成文，则在 PRD 中给出受控引用和冻结门。
- **medium** Agent 基准数字缺少判分协议（SM-04、SM-05）— “条件解析正确”“代表性任务”“两轮自修复”和“静默编造”没有语料分层、裁决方法、随机性控制或版本规则，不同团队可在同一数字下得到不同结论。*Fix:* 定义版本化基准集规范、任务类别与难度配额、golden result/人工裁决规则、模型和温度固定方式、失败计数及置信区间或重复运行要求。
- **medium** 部分性能门缺少完整测量条件（NFR-002–NFR-005）— 服务端参考环境不能单独决定浏览器可交互时间或 45 FPS；缓存状态、客户端硬件、浏览器、数据形状、并发采样窗口和 p95 样本量未固定。*Fix:* 为每项 NFR 增加客户端与服务端测试画像、冷/热缓存、数据集、并发、采样次数、计时起止点和通过规则。

## Scope honesty — adequate

`§6.3` 明确排除了实盘、全球资产、多租户、SaaS、社交、模型托管与公共 API；数据许可、无商用授权、第三方费用和远端单工作区风险也没有被藏起来。开放项有负责人和关闭时点，整体范围透明度很高。

唯一显著不一致在假设管理：addendum 明确称差异化是尚未验证的假设，而 `§13` 又说“无未确认的产品假设”。用户批准产品方向只能证明意图已确认，不能把市场需求与迁移价值变成已证事实。

### Findings

- **high** 假设索引错误地把“用户已批准”当成“外部命题已验证”（§13；addendum“竞品与邻近方案证据”）— “Agent 是核心竞争力”和“组合形态足以吸引真实用户”仍是待证市场假设，却未被索引或赋予验证负责人。*Fix:* 在愿景或战略段落内标记该差异化/需求假设，并在假设索引中记录证据现状、验证方法、负责人、关闭条件及对应的前置里程碑。

## Downstream usability — adequate

词汇表、四条具名旅程、连续 FR/NFR/SM 编号和按功能分组的要求，使 UX、架构与故事工作流可以稳定 source-extract。章节大多可以独立阅读，用户与 Agent 的行为边界也保持一致。

主要缺陷是成功指标后的“验证 FR”引用看似形成可追踪关系，实际并不能支撑这些 FR 的完成判断：任务完成或贡献数量被映射到大量未被测试的能力。这会让下游 QA 或发布治理误把活动指标当作覆盖证明。

### Findings

- **high** SM 到 FR 的验证映射存在范围错配与覆盖空洞（§10.1–§10.2）— 例如 SM-01 的一次安装/Agent 查询声称验证 FR-065 至 FR-076，却无法验证备份迁移、秘密保护和完整诊断；SM-09 的贡献者与合并数量无法验证 FR-077 至 FR-083 的契约、权限、版本和兼容性；模拟组合 FR-044 至 FR-051 也没有对应的发布质量指标。*Fix:* 把“验证”改为精确的质量门映射：每个 SM 只引用它真实测量的要求，并为未覆盖的高风险 FR 增加独立验收套件或 release criterion；不必做大矩阵，但必须避免虚假覆盖。

## Shape fit — strong

这是一个正式外部发布、会继续进入 UX、架构、Epic 和 Story 的多角色开发者/投资研究产品，当前“愿景与原则 → 具名旅程 → 分组 FR → 横切治理/NFR → 成功指标/风险/开放项”的形状与 stakes 匹配。四条 UJ 都有具名主角且分别承担真实需求，不是 persona theater；addendum 也把技术机制和供应商证据从产品能力正文中移开，保持了 PRD 的职责边界。
